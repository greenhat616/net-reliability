# 测量结果

## 测试方法

`tools/net-bench.sh 0 0.1 0.2`，游戏 1.3.3，2026-10-15，Windows 11，单台机器。

- 独立服务器（`Server.jar`）和 Steam 客户端都在本机，经 127.0.0.1 直连 UDP，不走 Steam P2P。
- 每次运行都用同一个世界（`build/nettest/_world` 模板），出生点相同。
- 服务器把玩家依次传送到 5 个相距 250–500 格的位置，共两轮。客户端测量每次传送后，到它请求的区域全部加载完成所用的时间。第 1 轮包含服务器生成新地形的时间，第 2 轮回到已生成的地方，主要反映网络。
- 丢包在客户端加入之后才开启（`NETTEST_LOSS`），丢的是客户端**收到的**数据报，也就是服务器发来的区域数据。连接阶段如果也丢包，原版可能卡在连接界面好几分钟（10% 丢包时实测过一次），那测的就是另一回事了。
- "vanilla" 组关掉本 mod 的全部功能：`nackEnabled=false`、`socketBufferKB=0`。这一轮的 vanilla 组还开着合并 bug 修复（`fixVanillaMergeBug` 是后来加的），但它对 vanilla 组没有影响：在回环地址上分片不会乱序，第 0 片丢了原版也补不回来。之后的 `net-bench.sh` 会把它也关掉。

## 结果

每次传送后加载完成的平均时间（中位数）：

| 丢包率 | 组 | 第 1 轮 | 第 2 轮 | 分片包放弃数 | 游戏统计的 incomplete dropped |
|---|---|---|---|---|---|
| 0 | vanilla | 1187 ms（1199） | 1095 ms（1084） | 0 / 1249 | 0 |
| 0 | mod | 1172 ms（1168） | 1101 ms（1084） | 0 / 1249 | 0 |
| 10% | vanilla | 6102 ms（6883） | 5527 ms（5065） | 239 / 1477 | 235 |
| 10% | mod | 1920 ms（2136） | 2710 ms（2772） | 0 / 1249 | 0 |
| 20% | vanilla | 8112 ms（8393） | 9170 ms（8781） | 499 / 1734 | 495 |
| 20% | mod | 3567 ms（3243） | 4037 ms（4534） | 0 / 1244 | 0 |

（vanilla 组的分片包总数更多，是因为丢了的区域被游戏重新请求，服务器又发了一遍。）

10% 丢包时，mod 组有 197 个分片包是在 NACK 之后才收齐的，共发了 220 个 NACK，补发 220 片。

## 结论

- **无丢包时没有额外开销**：两组的加载时间、包数一样，没有发过 NACK。
- **有丢包时，分片包一个都没再丢。** 原版在 10% 丢包时有 16% 的分片包被整包丢弃（理论值：2 片的包是 1 − 0.9² = 19%），每个都要等 2 秒让游戏重新请求。加载时间：10% 丢包从约 5.5–6.1 s 降到约 1.9–2.7 s，20% 丢包从约 8.1–9.2 s 降到约 3.6–4.0 s。
- **剩下的时间主要花在单数据报的包上。** 1.3.3 里区域数据大多只有 1–2 片，约 2/3 的区域包只占一个数据报。这种包丢了接收方根本不知道，NACK 无能为力，仍然要等游戏 2 秒后重新请求。要消除这部分延迟，需要真正的可靠传输（ACK + 重传），这就是实验性的 KCP 选项的目的（[KCP.md](KCP.md)）。

## 局限

- 回环地址上没有真实的延迟、抖动和带宽限制，丢包是均匀随机的（真实网络的丢包往往是突发的）。
- 只测了服务器到客户端方向的丢包。
- 每组只跑了一次（共 10 次传送），没有算置信区间。差距足够大，结论不受影响，但具体数字只能看个大概。
