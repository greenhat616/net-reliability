# 测量结果

## 测试方法

`NETBENCH_GROUPS="vanilla mod kcp" tools/net-bench.sh 0 0.1 0.2`，游戏 1.3.3，2026-10-15，Windows 11，单台机器。

- 独立服务器（`Server.jar`）和 Steam 客户端都在本机，经 127.0.0.1 直连 UDP，不走 Steam P2P。
- 每次运行都用同一个世界（`build/nettest/_world` 模板），出生点相同，分片包数量也基本相同（约 1250 个）。
- 服务器把玩家依次传送到 5 个相距 250–500 格的位置，共两轮。客户端测量每次传送后，到它请求的区域全部加载完成所用的时间。第 1 轮包含服务器生成新地形的时间，第 2 轮回到已生成的地方，主要反映网络。
- 丢包在客户端加入之后才开启（`NETTEST_LOSS`），丢的是客户端**收到的**数据报，也就是服务器发来的数据。走 KCP 时丢的是 KCP 数据报。连接阶段如果也丢包，原版可能卡在连接界面好几分钟（10% 丢包时实测过一次），那测的就是另一回事了。
- 三组：
  - **vanilla**：本 mod 的功能全部关闭（`nackEnabled=false`、`fixVanillaMergeBug=false`、`socketBufferKB=0`），即游戏自身的行为
  - **mod**：默认设置（NACK 补发 + 修正合并 bug + 4 MB socket 缓冲区）
  - **kcp**：默认设置，客户端再开 `kcpEnabled=true`（实验性）

## 结果

每次传送后加载完成的平均时间（括号里是中位数）：

| 丢包率 | 组 | 第 1 轮 | 第 2 轮 | 分片包放弃数 | 游戏统计的 incomplete dropped |
|---|---|---|---|---|---|
| 0 | vanilla | 1172 ms（1150） | 1095 ms（1078） | 0 / 1249 | 0 |
| 0 | mod | 1172 ms（1115） | 1097 ms（1082） | 0 / 1250 | 0 |
| 0 | kcp | 1178 ms（1150） | 1121 ms（1110） | 0 / 1250 | 0 |
| 10% | vanilla | 5131 ms（4815） | 6433 ms（6540） | 240 / 1480 | 218 |
| 10% | mod | 2326 ms（2413） | 2599 ms（2837） | 0 / 1250 | 0 |
| 10% | kcp | **1198 ms（1184）** | **1144 ms（1120）** | 0 / 1249 | 0 |
| 20% | vanilla | 12183 ms（12392） | 9990 ms（10336） | 566 / 1800 | 563 |
| 20% | mod | 3353 ms（3034） | 3730 ms（3084） | 0 / 1250 | 0 |
| 20% | kcp | **1194 ms（1147）** | **1161 ms（1132）** | 0 / 1249 | 0 |

补充说明：

- vanilla 组的分片包总数更多，是因为丢了的区域被游戏重新请求，服务器又发了一遍。
- vanilla 组 20% 丢包时，服务器的传送命令本身丢了 3 次。原版不会重发，测试驱动 30 秒后重发了传送。
- mod 组 10% 丢包时，203 个分片包在 NACK 之后收齐，共发 224 个 NACK、补发 224 片；20% 丢包时分别是 386、478、478。
- kcp 组的 KCP 数据报：0% 丢包时收 2859、发 2860，交给游戏的数据报 4079 个（流模式会把多个小数据报合并进一个 KCP 数据报）；20% 丢包时收 3088、发 3155。会话失败、被拒、发送被丢都是 0。

上表是 KCP 第二轮审查修复之前的代码（会话生命周期和上限方面的修改）。最终代码另跑了一次 KCP、20% 丢包、3 个位置 × 2 轮：两轮平均 1191 ms / 1133 ms，没有会话失败，和上表一致。

## 结论

- **无丢包时三组没有差别**：加载时间、包数一样，没有发 NACK，KCP 也没有额外延迟。
- **NACK（默认）消除了分片包丢失**：原版在 10% 丢包时约 16% 的分片包被整包丢弃（2 片的包理论上是 1 − 0.9² = 19%），每个都要等 2 秒让游戏重新请求。mod 组一个都没丢。加载时间：10% 丢包从 5.1–6.4 s 降到 2.3–2.6 s，20% 丢包从 10.0–12.2 s 降到 3.4–3.7 s。
- **剩下的延迟来自单数据报的包。** 1.3.3 的区域数据大多只有 1–2 片，约 2/3 的区域包只占一个数据报。这种包丢了接收方不知道，NACK 无能为力，仍要等游戏 2 秒后重新请求。
- **KCP（实验性）把丢包完全藏住了**：10% 和 20% 丢包时的加载时间与无丢包时相同（约 1.15–1.2 s），因为每个数据报丢了都会在几十毫秒内（回环地址上的 RTT 加上 KCP 的快速重传）重传，游戏完全感觉不到丢包。代价是在一个有序流里有队头阻塞，见 [KCP.md](KCP.md)。

## 局限

- 回环地址上的延迟几乎为零，没有抖动和带宽限制，丢包是均匀随机的（真实网络的丢包往往是突发的）。在高延迟链路上，KCP 重传要花一个 RTT 以上，NACK 也一样，差距会比这里小，但仍然远小于原版的 2 秒。
- 只测了服务器到客户端方向的丢包。
- 只测了区域加载时间，没有测移动的流畅度，而 KCP 的队头阻塞恰恰会影响移动。
- 每组只跑了一次（共 10 次传送），没有算置信区间。差距足够大，结论不受影响，但具体数字只能看个大概。
