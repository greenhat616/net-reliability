# KCP 传输（实验性）

`kcpEnabled = true`（客户端）时，通过 IP 加入服务器的连接改为跑在 KCP 上：所有游戏数据报都可靠、有序地送达，丢了由 KCP 重传。NACK 只能补救分片包，KCP 连单数据报的包也能补回来。

## 为什么用 KCP

| 方案 | 结论 |
|---|---|
| 只有 NACK（默认） | 只能补多片包缺的片。单数据报的包丢了，接收方不知道它存在 |
| Steam 可靠模式（`steamSendMode`） | 只适用于 Steam P2P，直连 IP 用不上 |
| TCP | 内核的拥塞控制和重传超时（RTO 下限通常 200 ms 以上，按指数退避）对游戏太保守 |
| QUIC | 功能最全，但 Java 实现很重（Netty 加原生库），对一个 mod 来说代价太大 |
| **KCP** | 一个文件的 ARQ 协议：选择性 ACK、快速重传、RTO 不翻倍（nodelay 模式下每次 ×1.5）、可以关掉拥塞窗口。MIT 许可，代码少，好移植，好审查 |

KCP 的作者说它用多 10–20% 的带宽，换来平均延迟降低 30–40%（[skywind3000/kcp README](https://github.com/skywind3000/kcp)，这是作者自己的说法）。本 mod 的实测见 [RESULTS.md](RESULTS.md)。

## 实现

`kcp/Kcp.java` 是 `ikcp.c` 的 Java 移植，结构和字段名尽量与 C 源码一致，方便逐行对照。上游的版权声明保留在类注释里。

- 移植自上游提交 `7346e366f1928dd727ecbb53253454fdaecaebb7`。和上游一样定义了 `IKCP_FASTACK_CONSERVE`：比某个段最近一次发送更早的 ACK，不计入它的快速重传计数。
- 只移植了上游默认的拥塞控制路径；可插拔的 `ccops`、日志、自定义内存分配都没有移植。
- 修改它之前，先对照上游同一提交的源码。

### 线路上的格式

KCP 输出的每个数据报，都包装成一个**普通的单数据报游戏包**，类型是 `PacketKcpSegment`：

```
[游戏的非分片包头：split 位 = 0、u16 包类型 = PacketKcpSegment、无时间戳]  [KCP 数据报（24 字节头 + 数据）]
```

这样游戏原有的接收循环（`ClientAddressNetwork`、`*ServerOpenNetwork`）能正常解析它，不会报"未知包"，然后照常交给 `PacketManager.submitInPacket`。本 mod 在那里把它截下来交给 KCP，不交给游戏。包头字节是在启动时从一个空的 `PacketKcpSegment` 现场生成的，不是硬编码的。

KCP 用流模式。流里每个游戏数据报的格式是 `u16 长度 + 原始字节`。KCP 吐出的完整数据报，用 `new NetworkPacket(info, bytes)` 还原后，提交给**同一个** `PacketManager`，就像它直接从网络到达一样。所以分片重组、`ServerClient` 识别、统计这些都照旧。

- MTU = 1024（游戏接收缓冲区大小）− 包头长度，所以每个 KCP 数据报都能被游戏的 1024 字节缓冲区收下。
- 参数：`nodelay=1`、`interval=kcpIntervalMs`（10）、`resend=kcpFastResend`（2）、关闭拥塞窗口、收发窗口都是 `kcpWindow`（256）。

### 协商

- **客户端决定。** `ClientAddressNetwork.openConnection()` 之后（`ClientOpenConnectionPatch`），如果 `kcpEnabled`，就为这个服务器地址建一个会话（随机 conv），之后发往该地址的所有数据报都走 KCP（`DatagramSendPatch` 拦下 `DatagramNetworkInfo.send`）。
- **服务器跟随。** 服务器从某个地址收到第一个 KCP 数据报时，用对方的 conv 建会话，此后发往这个地址的数据报也走 KCP。准入规则（数据报来自未经认证的地址）：
  - 必须开着 `kcpAcceptFromClients`。
  - 第一个数据报必须是这个 conv 的合法 KCP，**通过校验后才发布会话**。校验失败不留下任何状态。
  - 每个 IP 最多 4 个会话，总共最多 1024 个。
  - 同一地址出现另一个 conv 时：如果现有会话 10 秒内收到过合法数据，就忽略新的 conv（防止旧连接的迟到数据报，或者伪造的数据报，破坏正在使用的连接）。否则用新会话替换，旧 conv 进入"已退役"名单 60 秒，期间它的数据报一律忽略。一个地址 60 秒内最多退役 8 个 conv，名单满了就暂不接受这个地址的新会话，直到有条目过期。
- 客户端自己的 socket 从不接受别人发起的会话。
- **没有回退。** 服务器如果没装本 mod，或者 `kcpAcceptFromClients = false`，开了 KCP 的客户端就连不上（停在连接界面），这是实验性选项的已知限制。由于 `clientside = false`，游戏本来就要求双方装同样的 mod。

### 线程和锁

- KCP 数据报的输入、ACK 的发送、完整数据报交给游戏：都在游戏的接收线程里进行。
- `KcpSession.send`（游戏发包时）：在调用 `send` 的线程里进行。
- `update`（定时 flush、超时重传）：每 `kcpIntervalMs` 在 `NetReliability worker` 线程里运行一次。
- 每个会话一把锁。**持有会话锁时绝不获取其他锁**：交给游戏（会拿 `PacketManager` 的锁，还可能触发对其他会话的发送）是在 `input` 返回、释放锁之后才做的。

### 和其他功能的关系

- 走 KCP 的连接不再缓存分片，也不发 NACK（`KcpTransport.isReliable`）。
- 模拟丢包作用于网络上的 KCP 数据报，不作用于 KCP 交给游戏的数据报，所以测的是 KCP 的重传。
- **会话失败时不会悄悄退回普通 UDP。** 以下情况会话进入 FAILED 状态：
  - 某个段重传 20 次仍未确认（KCP 的 dead link）
  - 有未确认的数据，但 20 秒内确认没有任何进展
  - 待发送加未确认超过 2048 段（约 2 MB）
  - 流里出现超过 1024 字节的帧（流已损坏）
  - 暂存的分片超过 4 MB
  - 服务器端 30 秒收不到这个客户端的合法数据

  失败的会话会释放所有缓冲区，但作为"墓碑"保留下来：发往对方的数据直接丢弃，对方发来的数据报忽略，游戏自己的超时会断开这个连接。如果退回普通 UDP，对方可能还在用 KCP，两边就对不上了。墓碑在以下情况删除：
  - 这个玩家断开连接（`ServerClientDisconnectEvent`），见下文"正常关闭"
  - socket 关闭（包括客户端 `close()`）
  - 服务器端已失败超过 60 秒，且没有任何已连接的玩家使用这个地址（从未进入游戏的会话）
- **正常关闭。** 游戏断开连接时，会先发一个断开包（包含被踢的原因），然后才触发断开事件或关闭 socket。这个包此时只是排进了 KCP 的发送队列。所以：
  - 服务器端在断开事件之后，会话继续处理 ACK 和重传，直到队列被确认，最长 3 秒，然后删除。这期间对方发来的游戏数据一律丢弃：新的游戏连接必须用新的会话。删除后这个 conv 进入"已退役"名单，迟到的数据报不会让它复活。
  - 客户端在 `close()` 关闭 socket 之前，最多等 0.5 秒，让队列被确认（这段时间会阻塞关闭的线程）。
- **分片包整包交付。** KCP 交出的数据报如果是分片包的一片，先暂存，等这个包的所有分片到齐后一起交给游戏。原因：游戏的半成品包在最后一片到达 5 秒后过期，而 KCP 可能因为前面某个段丢了而卡住超过 5 秒，此时前面的分片已经被 KCP 确认，对方不会再发。暂存的是原始数据报（解析后的 `NetworkPacket` 会按包头声称的分片数分配数组，不能长期保留），每个会话最多 512 个包、4 MB，超过 60 秒的丢弃。超出上限、单个包超过 8192 片、或者同一个包的分片数前后不一致，会话直接失败。凑齐后按序号逐片解析并交给游戏，不会同时保留所有解析结果。
- Steam P2P 不受影响。

## 已知限制

- **队头阻塞。** 所有数据报在一个有序流里，一个段丢了，后面的数据（包括移动更新）都要等它重传完才交给游戏。丢包时移动可能有轻微的卡顿感，基准测试测不出这个。
- 每个 UDP 数据报多 24 字节 KCP 头，外加 3 字节包装，再加上 ACK 流量。流模式会把小包合并，部分抵消这些开销。
- 没有加密和认证（原版 UDP 也没有）。能伪造源地址的攻击者可以占满会话名额（只影响 KCP 客户端，普通 UDP 客户端不受影响），或者在一个连接安静超过 10 秒后替换它。原版游戏同样无法防御伪造源地址。
- `simulatedLossFragmentsOnly` 对 KCP 连接无效：KCP 数据报本身不是分片，KCP 交给游戏的数据报又不经过模拟丢包。
- 只在 127.0.0.1 上测过（见 [RESULTS.md](RESULTS.md)），没有在真实的广域网上测过。
